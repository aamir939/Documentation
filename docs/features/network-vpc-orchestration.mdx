# Network VPC & Subnet Orchestration

**Business Value:** Multi-tenant GPU infrastructure requires bulletproof network isolation. Dflair AI automates VPC and subnet lifecycle through integration with the Network Fabric Controller, giving tenants isolated virtual networks while abstracting away the complexity of VRF/VLAN/VXLAN configuration.

## What is VPC/Subnet Orchestration?

In the GPUaaS platform, a **VPC (Virtual Private Cloud)** is a tenant-isolated virtual network built on top of physical switches using VRF (Virtual Routing and Forwarding) technology. Each VPC provides a completely isolated routing domain — traffic from one tenant's VPC cannot reach another tenant's VPC unless explicitly allowed.

A **Subnet** is a segment within a VPC. Each subnet has a VLAN ID, a CIDR block (IP range), a gateway, and ACL rules. Subnets are where GPU nodes, control planes, load balancers, and worker nodes actually connect.

### Network Hierarchy Overview

<Drawio content={networkHierarchy} />

The platform automates VPC and subnet lifecycle through the **network-orchestration-service** microservice, which talks to the Network Fabric Controller to program the physical switches. From the user's perspective, they create a VPC in the portal, add subnets, and assign them to projects — the underlying VXLAN/EVPN/VLAN configuration is handled entirely in the backend.

:::info VPC = VRF, Subnet = VLAN (Simplified)
In simple terms: a VPC maps to a VRF on the physical network (an isolated routing table on the switches), and a subnet maps to a VLAN/VXLAN segment within that VRF. The platform uses VXLAN with EVPN control plane for scalable L2/L3 overlay networking across the data center fabric.
:::

## Network Architecture

### Frontend Fabric (Ethernet)

The FE (Frontend) fabric is an Ethernet fabric that carries all management, control plane, and tenant Ethernet traffic. It uses VXLAN/EVPN for overlay networking with BGP underlay. The fabric is managed by the Network Fabric Controller, which provides a centralized API for programmatic VRF/VLAN/subnet provisioning.

### VRF Types (The Foundation of VPCs)

The FE fabric has five categories of VRFs, each serving a distinct purpose:

| VRF Type | Purpose | Who Uses It | How VPCs Relate |
|----------|---------|-------------|-----------------|
| **Admin VRF** | Hosts all management traffic for the orchestration portal. Provides routed connectivity into tenant provisioning VRFs and tenant control plane VRFs. | Platform ops, orchestration portal, provisioning controller | Not tenant-visible. This is the platform's internal management network. |
| **Provisioning VRF** | Dedicated to initial bootstrapping of GPU nodes. Provides DHCP relay/forwarding to the Provisioning Controller for PXE-based OS provisioning. | Bare metal provisioning service, GPU nodes during PXE boot | Not tenant-visible. Used only during bare metal provisioning phase. |
| **Tenant VRFs (Pool of 10)** | Dedicated per-tenant. Carries GPU worker registration, cluster control plane access, workload data plane, and storage over Ethernet. Each tenant gets 4 VLANs per VRF. | Tenants, GPU worker nodes, K8s/Slurm clusters | **This IS the tenant's VPC.** When a user creates a VPC in the portal, it maps to one of these pre-created tenant VRFs. |
| **Outside Infra VRF** | Connects the data center to external infrastructure. Provides reachability for DNS, NTP, Syslog, LDAP/AD, and other shared services. | All nodes (shared services access) | Not tenant-visible. Provides shared service connectivity to all VRFs. |
| **VRF Default (Infra)** | Underlay VRF for the FE fabric. Basic IP reachability between fabric switches, loopbacks, and underlay BGP routing. | Fabric switches only | Not tenant-visible. The physical transport that carries all overlay VRFs. |

### Backend Fabric (InfiniBand)

Separate from the Ethernet FE fabric, an **InfiniBand backend fabric** managed by the InfiniBand Fabric Manager handles GPU-to-GPU communication. Tenant isolation on IB is achieved via **PKeys (partition keys)** — each tenant gets a unique PKey, and only their GPU nodes' InfiniBand GUIDs are added to that partition. This ensures GPU-to-GPU RDMA traffic is completely isolated between tenants.

## Portal Operations

From the portal, users interact with VPCs and subnets as logical networking constructs. They don't see VRFs, VLANs, fabric controllers, or switches.

| Action | What the User Does in Portal | What It Maps To (Backend) |
|--------|------------------------------|---------------------------|
| **Create VPC** | Names the VPC, selects project/org assignment | Allocates a pre-created tenant VRF from the pool. Links VRF ownership to tenant/org/project in orchestration DB. |
| **Add Subnet to VPC** | Specifies subnet name, CIDR, gateway. Selects purpose (control plane, workers, LB, data) | Allocates a pre-created VLAN within the tenant VRF. Each tenant VRF has 4 VLANs available for: (1) control plane, (2) GPU workers, (3) load balancer, (4) data plane. |
| **Allocate Existing Network** | Selects a pre-created network segment by ID/name | Links the existing fabric network (VRF + VLAN + subnet) to the tenant's project. No new fabric config needed. |
| **View VPC Details** | Sees: VPC name, subnets, CIDR ranges, gateway IPs, associated clusters | Reads from orchestration DB (MongoDB/PostgreSQL). Shows the logical view of the VRF + VLANs. |
| **Assign VPC to Cluster** | During K8s/Slurm cluster creation, selects which VPC/subnet for CP, workers, LB | The selected VLANs are configured on the GPU nodes' switch ports. Cluster networking uses these VLANs. |
| **Delete Subnet** | Removes a subnet from VPC (must have no active clusters) | Deallocates VLAN. Returns to pool. Fabric config may be retained or cleaned up depending on policy. |
| **Delete VPC** | Removes entire VPC (all subnets must be empty) | Deallocates tenant VRF. Returns to pool. Fabric VRF unlinked from tenant. |

### Flow 2: Allocate Pre-Created Network

In production, tenant networks are often pre-created by the fabric admin to ensure consistency and compliance:

| Step | Action | Description |
|------|--------|-------------|
| 1 | **Admin Pre-Creates** | Fabric admin creates network segment in the Network Fabric Controller: VLAN/VXLAN ID, subnet, gateway, ACLs, routing policies, L3 out gateway towards firewall, default firewall rules for shared services. |
| 2 | **User Requests** | Tenant requests VPC allocation via portal. Selects the pre-created network by reference ID/name. |
| 3 | **Ownership Update** | Portal calls network-orchestration-service with action: Allocate VPC / Allocate Subnet + tenant/org/project ID + pre-created network reference. |
| 4 | **Metadata Link** | network-orchestration-service updates ownership in orchestration DB. No fabric controller API call needed — network already exists on switches. |
| 5 | **Ready** | Tenant can now deploy clusters and workloads on the assigned network. |

:::tip Pre-Created vs Dynamic
In the current GPUaaS deployment, most tenant networks are **pre-created (Flow 2)** for tighter control. Dynamic creation (Flow 1) is available but requires additional firewall configuration post-creation. The platform supports both models.
:::

## VLAN Architecture

:::note Deployment-Specific Values
The VLAN IDs, IP ranges, and network configurations shown below are examples. Actual values are configured per deployment based on site requirements.
:::

### Admin VRF VLANs (Platform Infrastructure)

| VLAN ID | Name | CIDR | Gateway | Purpose |
|---------|------|------|---------|---------|
| `<ADMIN-VLAN-1>` | Admin/Tunnel | `<PLATFORM-NET-1>/24` | `<GW-1>` | Administrative tunnel traffic between orchestration components |
| `<ADMIN-VLAN-2>` | Mgmt / Frontend UI | `<PLATFORM-NET-2>/24` | `<GW-2>` | Portal, agents, management API traffic |
| `<ADMIN-VLAN-3>` | Provider Tenant | `<PLATFORM-NET-3>/24` | `<GW-3>` | DHCP relay from GPU nodes to Provisioning Controller for PXE boot |
| `<ADMIN-VLAN-4>` | Storage | `<PLATFORM-NET-4>/24` | `<GW-4>` | Platform object storage connectivity (S3 endpoints) |

### GPU Server Inband VLANs (Per Compute Unit)

Each Compute Unit has a dedicated inband VLAN for GPU server OS provisioning and management:

| VLAN ID | VRF | Network | Subnet Mask | Purpose |
|---------|-----|---------|-------------|---------|
| `<CU-VLAN-1>` | CU1-Inband | `<INBAND-NET-1>` | /26 | Compute Unit 1 provisioning |
| `<CU-VLAN-2>` | CU2-Inband | `<INBAND-NET-2>` | /26 | Compute Unit 2 provisioning |
| `<CU-VLAN-N>` | CUN-Inband | `<INBAND-NET-N>` | /26 | Additional compute units as deployed |

### Tenant VRF VLANs (Per-Tenant VPC Networks)

Each tenant gets 4 VLANs from a pre-created pool. The pool is sized per deployment (e.g., 10 tenant VRFs with 4 VLANs each = 40 VLANs):

| Tenant | VLANs | Subnets | VLAN Purpose (4 per tenant) |
|--------|-------|---------|----------------------------|
| Tenant 1 | `<T1-VLAN-1..4>` | `<T1-SUBNET-1..4>/24` | VLAN 1: Control Plane / Login nodes \| VLAN 2: GPU Workers / data plane \| VLAN 3: Load Balancer \| VLAN 4: Additional / future use |
| Tenant 2 | `<T2-VLAN-1..4>` | `<T2-SUBNET-1..4>/24` | Same 4-VLAN structure per tenant |
| Tenant N | `<TN-VLAN-1..4>` | `<TN-SUBNET-1..4>/24` | Pattern continues for all tenants |

:::info 4 VLANs Per Tenant — Why?
Each tenant needs isolated subnets for:
1. **Control Plane** — where K8s API server / Slurm controller endpoints live
2. **GPU Workers** — where bare metal GPU nodes connect for workload data plane traffic
3. **Load Balancer** — isolated ingress/egress for external access to tenant services
4. **Additional** — reserved for future use or specialized traffic

This 4-VLAN model ensures no cross-tenant traffic leakage at the network level.
:::

## What the Network Fabric Controller Configures on Switches

When the network-orchestration-service calls the Network Fabric Controller, here is what gets programmed on the physical leaf and spine switches:

| Config Element | What It Is | What Gets Created on Switches |
|----------------|------------|-------------------------------|
| **VRF Instance** | Isolated routing table | `vrf context TENANT-1-VRF` with unique VNI (VXLAN Network Identifier). All routes for this tenant are isolated in this routing table. |
| **VLAN** | Layer 2 broadcast domain | `vlan <id>` with name, mapped to VXLAN VNI. Each VLAN carries one subnet. |
| **VXLAN Segment** | Overlay tunnel | VXLAN encapsulation for the VLAN. Allows the VLAN to span across multiple leaf switches without traditional L2 flooding. |
| **SVI (Gateway)** | Layer 3 interface for subnet | `interface vlan <id>` with IP address (gateway), assigned to the tenant VRF. This is the default gateway for all devices on this subnet. |
| **EVPN Configuration** | Control plane for VXLAN | BGP EVPN address family with route-target import/export for the VRF. Distributes MAC and IP routes across the fabric. |
| **ACLs** | Access control lists | Permit/deny rules on the SVI or VRF: which subnets can talk to which, what shared services are reachable, firewall policy enforcement points. |
| **L3 Out (External)** | External routing | L3 out gateway towards enterprise firewall. Enables routed traffic between tenant VRF and shared services or orchestration layer. |
| **Switch Port Config** | Physical port assignment | When a GPU node is assigned to a tenant, its physical switch port is configured with the tenant's VLAN (trunk or access mode). |

## VPC/Subnet in Platform Workflows

### During Bare Metal Provisioning

| Step | Network Action | VLANs Used |
|------|----------------|------------|
| PXE Boot | GPU node's NIC broadcasts DHCP Discover on its Compute Unit Inband VLAN | Compute Unit Inband VLANs |
| DHCP Relay | DHCP request relayed to Provisioning Controller | Provisioning VLAN |
| OS Install | Golden image downloaded from provisioning service over Compute Unit Inband VLAN | Compute Unit Inband VLANs |
| Agent Connect | Agent connects to portal over management network | Management VLAN |

### During Cluster Creation

| Step | Network Action | VLANs Used |
|------|----------------|------------|
| VIP/LB Creation | Control plane VIP created on tenant CP subnet | Tenant VLAN 1 (Control Plane) |
| Worker Join | GPU workers join K8s cluster over tenant network | Tenant VLAN 2 (GPU Workers) |
| CNI Overlay | Calico/Cilium creates pod overlay network on top of tenant VLAN | Tenant VLAN 2 (IP-in-IP/eBPF overlay within) |
| LB Assignment | External-facing LB IPs allocated from tenant LB subnet | Tenant VLAN 3 (Load Balancer) |
| Agent Instructions | Portal sends bootstrap/deployment via agent gRPC | Management VLAN |

### During Workload Execution

| Traffic Type | Network Path | Protocol |
|--------------|--------------|----------|
| GPU-to-GPU (training) | InfiniBand backend fabric (PKey isolated) | RDMA / GPU collective libraries (400G links) |
| GPU-to-Storage | InfiniBand → High-performance parallel filesystem | Lustre / RDMA |
| Pod-to-Pod | Tenant VLAN via CNI overlay (Calico/Cilium) | Overlay (IP-in-IP / eBPF) |
| External access | Tenant LB VLAN → Ingress Controller | HTTP/HTTPS |
| Monitoring metrics | Management VLAN / internal cluster | HTTP (Prometheus endpoints) |

## Firewall Rules & ACLs

An enterprise firewall sits between the orchestration layer and GPU nodes. Three levels of ACLs are enforced:

### Management Traffic ACLs

- **PXE reachability:** Provisioning Controller → GPU BMC nodes for OS provisioning and boot device control
- **IPMI reachability:** Provisioning Controller → GPU BMC for power on/off, boot device setting
- **Orchestrator IPMI access:** Portal default network access to IPMI interfaces for BM console access
- **Shared services:** All nodes → Proxy, DNS, NTP, Syslog, SSH via Outside Infra VRF

### Tenant Network ACLs

- **CP → Worker:** Control plane to GPU worker node communication over tenant network
- **IP-in-IP overlay:** GPU-to-GPU overlay communication for CNI (Calico/Cilium) pod networking
- **Agent connectivity:** Connectivity agent communication for control plane connectivity between managed CP and GPU workers

### Other Connectivity

- **Shared storage:** GPU nodes to external storage platforms (parallel filesystem over IB, object storage over Ethernet)
- **Multi-tenant isolation:** Additional fabric isolation requirements enforced per-VRF to prevent cross-tenant traffic

:::warning Firewall Configuration
Firewall rules for new tenant networks currently require manual admin action post-network creation. The platform creates the VRF/VLAN automatically, but the enterprise firewall rules must be configured by the network admin team to allow the required traffic paths.
:::

## Network Security Model

| Layer | Mechanism | Details |
|-------|-----------|---------|
| **Tenant Isolation** | VRF (separate routing table per tenant) | Each tenant VPC is a dedicated VRF on the physical switches. No route leakage between tenants. VXLAN/EVPN ensures overlay isolation. |
| **Subnet Isolation** | VLAN + ACLs | Each subnet is a separate VLAN within the VRF. ACLs restrict inter-subnet communication to only what's required. |
| **IB Isolation** | InfiniBand PKey (partition key) | InfiniBand GPU-to-GPU traffic isolated per tenant. Only GPU InfiniBand GUIDs belonging to the tenant are added to the PKey. |
| **Firewall** | Enterprise firewall between orchestration and GPU nodes | Stateful firewall with per-tenant rules. L3 Out from each tenant VRF routes through firewall. |
| **Authentication** | Keycloak OAuth2/JWT | All network API calls require valid JWT. Tenants can only manage their own VPCs. |
| **Transport** | TLS 1.2+, mTLS, HSTS | All API communication encrypted. Fabric controller API calls use TLS. |
| **Audit** | Centralized logging, S3 backup every 6hrs | All network create/delete/modify operations logged with correlation ID. SIEM integration in progress. |
